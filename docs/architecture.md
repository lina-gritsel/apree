# Решения и границы

## Один продукт, два приложения

`apps/web` — React SPA, `apps/api` — NestJS API. npm workspaces позволяют использовать один lockfile и запускать проверки из корня. Отдельного сервиса для каждой операции и общих пакетов для нескольких типов нет: объем задачи этого не требует.

Vite подходит для одной интерактивной доски: SSR и индексируемые страницы здесь не нужны. Material UI дает доступные примитивы, а единая тема определяет визуальный язык. TanStack Query хранит серверное состояние и управляет повторными загрузками; состояние формы остается рядом с формой.

На сервере контроллер отвечает за HTTP, DTO — за валидацию, сервис — за операции с задачами. Prisma обеспечивает типизированные запросы и версионирование схемы; PostgreSQL хранит данные независимо от процесса приложения.

В корневом `package.json` закреплен override `deepmerge-ts` для `@prisma/config`: он устраняет предупреждение аудита в транзитивной зависимости Prisma. Совместимость проверяется генерацией клиента, миграциями и тестами.

## Структура и обязанности

```text
apps/web/src/
  app/                     Компоновка приложения, тема и навигация
  shell/                   Шапка, боковая панель и знак
  shared/api/              HTTP-запросы и общие ошибки сети
  features/tasks/
    api/                   Контракт HTTP для задач
    model/                 Типы, фильтры, состояние доски и черновика
    components/
      board/               Канбан, список и переключение вида
      create/              Создание задачи
      detail/              Страница, активность и комментарии
      shared/              Свойства, вложения и общие элементы задач
  features/users/
    api/                   Контракт HTTP для участников
    model/                 Типы, загрузка и создание участников
    components/            Выбор исполнителя и аватар
apps/api/src/
  tasks/                   HTTP-контроллер, DTO, операции и история задач
  users/                   Участники и валидация их данных
  prisma/                  Подключение к PostgreSQL
```

`useTasks` отвечает за серверный кеш и мутации, `useBoardState` — за вид и фильтры, `useTaskDraft` — за несохраненные изменения, нормализацию и сохранение. Компоненты страницы используют эти функции, не выполняя HTTP-запросы напрямую. `useUsers` управляет загрузкой и созданием участников; поиск и открытие меню остаются локальным состоянием выбора исполнителя.

На сервере разбор вложений отделен от запросов к БД; состав возвращаемых данных задан отдельно. `describeChanges` собирает сообщения из небольших функций для полей, меток и файлов. Изменение задачи и запись события выполняются в одной транзакции; блокировка строки обеспечивает корректное предыдущее значение для истории.

E2E-сценарии разделены на `board`, `views`, `detail` и `assignee`. Общая fixture хранит только идентификаторы созданных данным тестом задач и проверяет их удаление, не затрагивая другие данные.

## Контракт

Задача содержит `id`, `title`, `description`, `priority`, `status`, `labels`, `attachments`, `assigneeId`, `assignee`, `createdAt`, `updatedAt`. Приоритеты: `low`, `medium`, `high`; статусы: `new`, `in_progress`, `done`.

| Метод  | Путь             | Назначение                      |
| ------ | ---------------- | ------------------------------- |
| GET    | `/api/tasks`     | Список задач                    |
| GET    | `/api/tasks/:id` | Одна задача                     |
| POST   | `/api/tasks`     | Создание                        |
| PATCH  | `/api/tasks/:id` | Изменение полей, включая статус |
| DELETE | `/api/tasks/:id` | Удаление                        |
| GET    | `/api/health`    | Liveness процесса API           |

Дополнительные операции:

| Метод | Путь                                 | Назначение                            |
| ----- | ------------------------------------ | ------------------------------------- |
| GET   | `/api/tasks/:id/activity`            | События и комментарии по времени      |
| POST  | `/api/tasks/:id/comments`            | Комментарий с необязательными файлами |
| GET   | `/api/tasks/:taskId/attachments/:id` | Скачивание файла                      |
| GET   | `/api/users`                         | Участники                             |
| POST  | `/api/users`                         | Создание участника                    |

Пример создания:

```json
{
  "title": "Проверить мобильную версию",
  "description": "Создание и изменение статуса с телефона",
  "priority": "high",
  "status": "new"
}
```

Фронтенд не считается доверенным источником: API самостоятельно проверяет поля и допустимые значения. Идентификатор отсутствующей задачи возвращает 404.

## Взаимодействия

Перетаскивание за любую часть карточки меняет статус задачи; обычный клик открывает отдельную страницу `/tasks/:id`. Она поддерживает прямые ссылки, перезагрузку и историю браузера. Центральное модальное окно используется для создания. Меню смены статуса доступно независимо от drag-and-drop, в том числе с клавиатуры и на мобильном экране. При неудачном сохранении статуса интерфейс возвращает предыдущее состояние. Ошибка сохранения формы не уничтожает введенный текст.

Поиск и фильтр выполняются на клиенте по уже загруженным данным. Это осознанное ограничение небольшой доски: при росте объема данных нужны серверная фильтрация и пагинация. Положение карточки внутри колонки не хранится; перетаскивание служит смене статуса.

Доска и сгруппированный список используют общий набор данных и фильтров; выбранный вид сохраняется локально. Исполнители — записи участников в PostgreSQL, задача хранит ссылку на участника. Создание участника и назначение доступны из формы задачи.

Комментарии и события изменения сохраняются в PostgreSQL и отображаются в разделе активности задачи. Это реальная история действий, а не демонстрационные записи интерфейса.

## Метки и вложения

Метки сохраняются вместе с задачей. Вложения — настоящие файлы: клиент передает новые файлы как `{ name, contentType, dataBase64 }`, уже сохраненные — как `{ id }`. API хранит байты в PostgreSQL и возвращает метаданные; скачивание выполняется через `GET /api/tasks/:taskId/attachments/:attachmentId`. В списке задач возвращаются только `id`, `name`, `contentType`, `size` вложения, без содержимого файла. Максимум три файла по 2 MiB в самой задаче и отдельно в каждом комментарии. Файлы комментариев не входят в список вложений задачи и не удаляются при редактировании этого списка. Для небольшой доски это сохраняет простой воспроизводимый запуск; при увеличении объема файлов стоит перейти на объектное хранилище.

## Ограничения

- Одна общая доска, без учетных записей, ролей и приватности отдельных задач.
- Нет live-синхронизации между пользователями; одновременное редактирование использует последнее сохраненное значение.
- Нет ручной сортировки, дедлайнов и нескольких проектов.
- Docker Compose рассчитан на воспроизводимый запуск и проверку. Публичное развертывание требует аутентификации, TLS и отдельных секретов.

## Что проверять

API-тесты защищают валидацию и операции; frontend-тесты — значимое поведение интерфейса. Playwright использует настоящий API и PostgreSQL: создание, изменение, смена статуса, перезагрузка и удаление. Отдельные браузерные сценарии проверяют ошибки, перетаскивание и мобильный экран. Реальные выполненные проверки и их результат фиксируются в отчете передачи, а не выводятся из наличия файлов тестов.

## Визуальная система

Визуальный ориентир — предоставленные пользователем скриншоты Linear: темная доска, компактные панели, четкая иерархия и центральное окно создания задачи. Это собственная реализация на Material UI, без использования библиотеки компонентов Linear. Apri использует знак из favicon официального портала Apree (источник указан в `apps/web/public/ASSET-SOURCES.txt`), общую тему MUI и переиспользуемые компоненты карточки, статуса и приоритета. В интерфейсе нет рекламного вводного блока и декоративных элементов без функции.
